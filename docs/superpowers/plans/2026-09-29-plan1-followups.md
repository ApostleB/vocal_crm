# 계획 1 실행 후 남은 항목 (계획 2·3 작성 시 반영)

계획 1(핵심 앱)은 2026-09-29 main 에 완료되었다. 테스트 25개 파일 94개 통과, 빌드 성공.
실제 앱을 띄워 11개 사용 흐름도 점검했고, 모두 통과했다.
작업별 리뷰와 최종 리뷰에서 나온 지적 중 이번에 고치지 않은 것을 옮겨 둔다.

## 계획 2(지점 이동·엑셀) 시작 전에 할 것 — store 보강

가져오기와 엑셀 명단 등록이 같은 store 함수를 타기 때문에, 계획 2 의 첫 작업으로 둔다.

- `savePass` 새 기록: 고객 존재 확인이 없다. 없는 고객이면 FK 오류가 나서 일반 오류 문구만 보인다. 수정 시 `customerId` 불일치도 무시된다.
- `saveLesson` 에 `reservationId` 를 직접 넘기면, 그 예약이 같은 고객의 `scheduled` 예약인지 확인하지 않고 `done` 으로 바꾼다.
- `gender`·`purpose`·`toStatus` 값을 store 에서 검증하지 않는다. 틀린 값은 SQLite CHECK 오류가 되어 일반 오류 문구로만 보인다. 엑셀·.vcrm 입력 경로 전에 AppError 로 검증한다.

## 계획 3(안전장치·배포)에 넣을 것

- `will-navigate` 차단: 파일을 창에 끌어다 놓으면 다른 페이지로 이동할 수 있다. `shell.openExternal` 은 https 만 허용한다.
- DB 열기 실패 처리: 파일이 잠겼거나 손상되면 창 없이 조용히 실패한다. 무결성 검사와 함께 `dialog.showErrorBox` 와 복원 안내를 넣는다.
- (완료) 더 새 버전의 DB 는 `DB_TOO_NEW` 로 거부한다. 계획 3 의 백업 복원에서 이 오류를 안내 문구로 연결한다.

## 사용하면서 결정할 UX

- 휴강에서 돌아올 때도 이력에 "재등록"으로 남는다. "휴강 복귀"로 따로 표시할지 사용자에게 확인한다.
- 예약 시간 직접 입력: 설계 5.5 는 "직접 입력 시 10분 단위로 맞춤"이다.
  - 지금은 검색 가능한 Select 라 10분 단위 값만 고를 수 있다. "15:0" 처럼 입력하면 후보가 걸러진다.
  - "1505" 같은 자유 입력을 가장 가까운 10분으로 맞추는 동작은 없다. 필요하면 추가한다.
- 조회 실패 알림 제목도 "저장하지 못했습니다"로 나온다. 설정 조회가 실패하면 시작 화면이 로딩 상태로 멈춘다. 계획 3 의 오류 처리에서 정리한다.

## 표시·품질 (급하지 않음)

- 같은 고객의 예정 예약이 여러 건(지난 미기록 + 오늘)이면 모두 같은 "N회차"로 보인다.
- 예약 창에서 날짜를 바꾼 직후 그날 예약을 불러오기 전에 저장하면 겹침 확인을 건너뛸 수 있다. 불러오는 동안 저장 버튼을 막는다.
- 예정 예약의 칩 취소 후 취소선은 자동 점검에서 직접 확인하지 않았다(로직 단위는 테스트됨).
- 테스트 보강 후보: 고객 삭제·닫기 확인·등록 후 이동 UI, 홈의 미기록 모달·검색·정렬, 상세 화면의 목표·공통메모·수강권 조작, 일정 칩 색·메뉴, `listLessons` 정렬, 기간 조회의 취소 예약 포함.
- 코드 정리 후보:
  - `requireDate` 가 `validation()` 대신 AppError 를 직접 생성한다.
  - `withEuro` 가 `trim()` 을 중복 호출한다.
  - 홈 패널의 행 테두리 스타일이 반복된다.
  - 예약 기간 조회가 매번 전체 고객 집계를 다시 계산한다(지금 규모에서는 무해).
- 커밋 `657cae9`, `144f79c` 의 Co-Authored-By 줄이 다른 모델명으로 들어가 있다. 히스토리는 다시 쓰지 않는다.
